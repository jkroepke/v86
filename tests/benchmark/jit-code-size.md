# JIT code size measurements

Measured on 2026-11-13 against `174ed682` (the emulator code is the same as
`b7c0670e`). Node 24.22.1, V8 13.6.233.17-node.58, Rust 1.100.0,
x86_64 Linux. Raw measurements and input hashes are in
[jit-code-size-results.json](jit-code-size-results.json).

## Changes

- Keep the inline TLB lookup and existing Rust slow helpers. Put each cold
  memory path inside an `if`, removing its surrounding block and `br_if`.
- Test the defined TLB permission/IO flags with a one-byte mask. Bits 7..11
  are unused in the current TLB entry representation. Reads/writes save
  three bytes per access; read-modify-write also saves one `eqz` byte.
- Fold an immediately adjacent `local.set n; local.get n` into `local.tee n`,
  saving two bytes. Track instruction boundaries explicitly, including i64
  locals; never scan arbitrary immediate bytes for opcodes.

Module entry/exit handling, register spills, the interpreter, dispatcher
structure, extra-block limit, and JIT threshold are unchanged. Memory slow
helpers were already out of line, so no extra fast-path helper calls were added.

## Fixed Linux code corpus

The Buildroot workload captured 161 32-bit code-page/entry-point samples.
Both builds recompiled the **same captured bytes**, entry offsets and cached
state flags, with paging off and one page per module. The debug cores are
required for the existing `jit_force_generate_unsafe` export. This isolates
code generation from differences in which pages a live guest makes hot.
These are single-entry page compilations, rather than the default three-page
modules generated while a complete guest is running.

| Metric | Before | After | Change |
|---|---:|---:|---:|
| Generated wasm bytes | 1,413,083 | 1,363,989 | -3.47% |
| Bytes per compiled page | 8,776.91 | 8,471.98 | -3.47% |
| Eager instantiate wall time | 70.89 ms | 65.67 ms | -7.36% |
| Eager instantiate process CPU | 66.37 ms | 61.72 ms | -7.00% |
| Default instantiate wall time | 34.46 ms | 27.82 ms | -19.28% |
| Code generation wall time | 60.83 ms | 60.27 ms | -0.93% |

152 samples became smaller, nine stayed equal, none grew. Timing values are
medians of seven fresh processes per build, with alternating order. Instantiation
was measured separately from guest execution and Rust code generation, using
captured modules and inert imports; no guest functions were called. Eager
measurements use V8's `--no-wasm-lazy-compilation` flag. Process CPU includes
compiler worker threads. The default and eager timings measure different
compiler configurations and should be assessed separately.

## Release runtime with pod-bench

The repository's `tools/pod-bench` booted the tabernetes v1.9.0 Linux VM,
restored it for each round, and ran linux/386 Alpine and nginx images.
`ab.sh` measured five rounds per build. The CPU workload checks matching
SHA-256 results after compression/decompression. nginx ends with an HTTP response.

| Workload / metric | Before | After | Change |
|---|---:|---:|---:|
| CPU workload wall time | 5,758 ms | 5,718 ms | -0.69% |
| CPU workload main-thread CPU | 5,740 ms | 5,690 ms | -0.87% |
| nginx startup wall time | 1,125 ms | 1,174 ms | +4.36% |
| nginx startup main-thread CPU | 1,110 ms | 1,170 ms | +5.41% |

These differences are within the repository's documented approximately 10%
noise range. Earlier three-round runs and an instrumented three-round repeat
are preserved in the results file as well; they show variation in nginx startup.
The measurements establish the byte reduction for this corpus; they do not
establish a precise runtime improvement. Spring/JVM and browser runs remain
unmeasured in this environment.

## Full Buildroot workload

The additional Linux harness boots `buildroot-bzimage68.bin`, warms up, then
alternates five checked three-million-iteration Lua loops with five batches of
30 BusyBox SHA-256 program starts. Three fresh release processes per build
produced the following medians (15 timed samples per phase):

| Metric | Before | After |
|---|---:|---:|
| CPU loop wall time | 1,652.80 ms | 1,600.40 ms |
| Program-start batch wall time | 4,457.21 ms | 4,326.30 ms |
| Total generated bytes per run | 16,102,992 | 15,338,913 |
| Total finalize-to-finished time per run | 2,234.24 ms | 2,052.28 ms |

One full profiler run per build reported:

| Counter / metric | Before | After |
|---|---:|---:|
| COMPILE | 162 | 167 |
| COMPILE_PAGE | 425 | 431 |
| COMPILE_WASM_TOTAL_BYTES | 31,421,630 | 31,720,013 |
| Bytes per compiled page | 73,933.25 | 73,596.32 |

Live runs compile different page/entry-point sets, and the profiler adds
substantial emitted code. Their total byte counts therefore do not isolate
compression of identical inputs. The fixed corpus above provides that comparison.
Finalize timing includes asynchronous scheduling, rather than compiler CPU alone.

## Reproduce

Keep separate release, profiler and debug wasm cores for the baseline and
changed tree. `make with-profiler` overwrites `build/v86.wasm`; remove that
output before `make build/v86.wasm` when switching back to a release core.
Run each comparison in a fresh Node process and alternate build order.

```sh
mkdir -p images
curl -fL https://i.copy.sh/buildroot-bzimage68.bin -o images/buildroot-bzimage68.bin
CORPUS_DIR=build/jit-code-size-corpus node tests/benchmark/jit-code-size.js /path/to/after-release.wasm
MODULE_DIR=/tmp/before-modules node tests/benchmark/jit-code-size-corpus.js /path/to/before-debug.wasm
MODULE_DIR=/tmp/after-modules node tests/benchmark/jit-code-size-corpus.js /path/to/after-debug.wasm
node --no-wasm-lazy-compilation tests/benchmark/jit-code-size-compile.js /tmp/before-modules
node --no-wasm-lazy-compilation tests/benchmark/jit-code-size-compile.js /tmp/after-modules
```

The corpus runner defaults to `build/jit-code-size-corpus`; an explicit second
argument selects another capture directory. Keep `MODULE_DIR` empty before
writing a new set of captured modules. The Linux harness also accepts
`MODULE_DIR` and `SERIAL=1`. For the pod workload, follow
[tools/pod-bench/README.md](../../tools/pod-bench/README.md), then run:

```sh
tools/pod-bench/ab.sh nginx 1 /path/to/before-build /path/to/after-build
tools/pod-bench/ab.sh cpu 1 /path/to/after-build /path/to/before-build
```

## Validation

- `make all-debug`: passed.
- `make rust-test`: passed, including i32/i64 folding, an intervening constant,
  a branch target, and builder reset.
- `make expect-tests`: all 27 passed. Reviewed and updated 18 changed snapshots.
- `make jitpagingtests`: passed, including shared/consecutive page writes and
  multipage self-modifying code, using the repository's Linux test image.
- ESLint for the changed JavaScript files: passed.
- Both NASM targets were attempted with `MAX_PARALLEL_TESTS=1`. Fixture
  generation is blocked: native execution of the 32-bit reference ELF reports
  `Exec format error`, and GDB reports startup exit code 127. Neither NASM suite
  completed. No CI run was available for the pushed branch at measurement time.

The old WABT 1.0.6 decoder could not parse current SIMD code, even with its
SIMD option enabled. WABT 1.0.39 now decodes it. The snapshot normalizer retains
the old local names/spelling to keep the diff focused. The existing SSE task
switch snapshot also needed its already-emitted v128 load/store updated.

The branch is for review and further benchmarking; both NASM suites still need
to pass on a host that can execute their reference binaries before merging.
